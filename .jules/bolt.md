## 2024-06-25 - [DOM Repaint Prevention & O(1) DOM Validations]
**Learning:** Found multiple opportunities to optimize core execution paths by replacing O(N) operations with O(1) validations, reducing overall overhead in base files like `BaseComponent.js`, `loadComponents.js`, and `autoMount.js`. Specifically:
1. `setAttribute` causes DOM invalidation and repainting even if the applied value matches the currently present attribute.
2. `Array.from()` conversions on native `NodeList` iterables cause excessive and unnecessary garbage collections for UI framework loading paths, iterating directly via `for` loops on NodeLists is vastly faster.
3. Checking if a specific node belongs to the Document root via `document.body.contains(node)` scales linearly O(N) up the DOM tree, whereas checking the node's native `isConnected` property provides O(1) lookup speeds.
**Action:** Always validate against existing attributes via `getAttribute` before executing `setAttribute` to intercept unnecessary mutation events. Prioritize standard `for` loops on natively iterable collections (like `NodeList` and `HTMLCollection`) over intermediate Array conversions. Replace `contains()` checks with `isConnected` checks when attempting to determine standard DOM attachments.

## 2024-08-01 - [Avoid String .split() in Hot Paths]
**Learning:** Found that string parsing with `.split()` generates unnecessary temporary arrays which increases memory allocations and garbage collection pressure in component initialization paths (like parsing data-actions). Using `indexOf()` and `substring()` is approximately 3-4x faster than `split()` for simple delimiter separations.
**Action:** Replace `split()` with `indexOf()` and `substring()` when extracting specific string segments, especially in loops like `_autoBindActions` iterating over multiple string items. Also, avoid `Array.from()` entirely for iterables (like Maps), instead iterating over `.keys()` directly with `for...of` loops to prevent array allocation overheads.

## 2025-02-12 - [Avoid Object.keys() in Hot Paths for Emptiness and Iteration]
**Learning:** Checking for object emptiness via `Object.keys(obj).length === 0` and iterating over object keys with `Object.keys(obj).forEach()` or `for (let i = 0; i < Object.keys(obj).length; i++)` forces the JavaScript engine to allocate a temporary array of all keys. In extremely hot paths like `setState` (called often during animations/scroll updates) or during high-volume component initialization routines like `set ref`, these temporary arrays create unnecessary garbage collection pressure and cause measurable slowdowns.
**Action:** Replace `Object.keys()` usage with native `for...in` loops accompanied by `Object.prototype.hasOwnProperty.call()` checks. For emptiness detection, use an early-exit `for...in` loop which is immediately O(1) in the best case, avoiding O(N) array allocation.

## 2024-05-11 - [Avoid String .split() and NodeList .forEach() in Action Binding]
**Learning:** Found that string parsing with `.split()` generates unnecessary temporary arrays which increases memory allocations and garbage collection pressure in component initialization paths (like parsing data-actions). Using `indexOf()` and `substring()` within a `while` loop is approximately 30-40% faster than `split()` for multiple delimiter separations, and doesn't generate temporary strings. Furthermore, iterating over a `NodeList` using a standard `for` loop avoids intermediate array allocations and overhead that `.forEach()` incurs.
**Action:** Replace `split()` with `indexOf()` and `substring()` when extracting specific string segments, especially in loops like `_autoBindActions` iterating over multiple string items. Use standard `for` loops for `NodeList` iteration.
## 2025-02-12 - [Avoid JSON.parse within Try/Catch in Hot Paths]
**Learning:** Checking for JSON validity via `try { JSON.parse(str) }` is extremely slow if the string is often not JSON, because generating and catching exceptions in JavaScript engines involves significant stack trace and unrolling overhead.
**Action:** Optimize string parsing by adding an early return/fast check like `if (str.startsWith('{') || str.startsWith('['))` before attempting `JSON.parse` to quickly bail out on primitive strings and prevent unnecessary exception handling.

## 2024-05-12 - Global Cache for State Attribute Conversions
**Learning:** Moving from a per-instance object cache (`this._stateAttributeCache`) to a module-level `Map` (`globalStateAttributeCache`) for storing `camelCase` to `kebab-case` state attribute conversions significantly reduces memory overhead and redundant regex parsing (`.replace()`) across components. Since state keys like `isOpen` and `isLoading` are frequently repeated across different instances, sharing a global `Map` avoids duplicating the same conversion for every single component instance. A global `Map` also performed slightly faster than a global Object in benchmark testing.
**Action:** When implementing lookup caches for values that are identical across instances (like key conversions or standard string formats), prefer a module-level `Map` rather than a per-instance property to save memory and skip duplicate computation.

## 2025-05-12 - [Avoid Redundant Object Allocation in setState Validation Loop]
**Learning:** Creating intermediate temporary objects (`const stateChanges = {}`) to store differences during state validation loops adds unnecessary heap allocations and triggers secondary iteration loops in high-frequency methods like `setState`. Building the batched internal structure directly inside the primary loop is noticeably faster.
**Action:** In hot loops, update the final destination structures (like `_pendingStateChanges` and `_pendingAttributeChanges`) directly inside the first validation pass (`this._state[key] !== changes[key]`), avoiding the creation and double-iteration of an intermediate object.

## 2024-05-13 - [Frame-rate Independent Smoothing Math]
**Learning:** Found that when calculating smooth deceleration or friction in requestAnimationFrame loops across varying frame rates (like 60Hz vs 144Hz displays), using linear scaling (e.g. `value += (target - value) * 0.1 * timeScale`) causes mathematical inconsistencies, resulting in different movement speeds depending on the monitor's refresh rate. Exponential smoothing (e.g. `value += (target - value) * (1 - Math.pow(0.9, timeScale))`) produces the exact same interpolated values over real time regardless of the frequency of frame executions. It's also slightly faster to compute in V8 than the linear multiplication.
**Action:** When implementing easing or friction on continuous properties, always apply frame-rate independent exponential smoothing `(1 - Math.pow(frictionBase, timeScale))` rather than linearly multiplying by `timeScale`. Ensure purely additive properties (like positional offset from raw velocity) still use simple linear `* timeScale`.
## 2025-05-13 - [Avoid Closure Allocation in requestAnimationFrame Hot Paths]
**Learning:** Found that defining inline anonymous closures for `requestAnimationFrame` (e.g. `requestAnimationFrame(() => { ... })`) inside hot-path methods like `setState` (which executes constantly during scroll or continuous animation updates) creates unnecessary heap allocations on every single frame. This increases garbage collection pressure and causes micro-stutters when the GC pauses execution to clean up thousands of temporary function objects.
**Action:** Extract inline `requestAnimationFrame` closures into permanent instance methods (e.g., `_flushStateChanges`) and pre-bind them in the component's constructor (`this._flushStateChanges = this._flushStateChanges.bind(this)`). Call `requestAnimationFrame(this._flushStateChanges)` to reuse the exact same bound function reference repeatedly without allocating new objects on each invocation.
